Context

Motivation

Why performance engineering matters in our daily work.

We constantly deal with:

File-driven workflows & constant data flux

Data moves through the system continuously — ingestion, transformation, export. Every pipeline step is a potential bottleneck.

Thousands of employees, growing file sizes & event volume

Scale compounds fast. What works at 1K rows can collapse at 1M. What survives 1M may not survive 1B.

Design is key to avoid unnecessary pressure on the entire system

Poor design choices don't just slow things down — they cascade across services, databases, and infrastructure.

Optimization 1/3

Binary Parsing

Target: String.split (~300ns) + Float.parse (~120ns) — the two biggest per-line costs.

[city, temp] = :binary.split(line, ";")

def parse_temp(<<?-, r::binary>>) do

-parse_digits(r, 0)

end

String.split :binary.split
Float.parse int ×10
String.split is Unicode-aware — grapheme clusters, UTF-8 state machine. Our data is pure ASCII. That's wasted work.
:binary.split scans raw bytes directly — right abstraction for the data.
Float.parse NIF handles sci notation, Inf, NaN — never needed here.
Fixed format -?D.D → pattern match + int ×10. Exploit domain constraints.

Optimization 2/3

ETS Storage

Target: Map.update (~160ns) — HAMT path copying and GC pressure.

case :ets.lookup(table, city) do

[{^city, min, max, c, s}] ->

:ets.insert(table, updated)

[] ->

:ets.insert(table, init)

end

Map (HAMT)
O(log₃₂ n) — path copy on every update
ETS
O(1) — mutable, outside process heap
Maps are HAMTs (branching factor 32). Depth ~2-3 for 413 keys. Every update rebuilds the leaf-to-root path.
Allocating is cheap; copying is not. 1B updates = billions of short-lived tuple allocations. The per-process GC must sweep them all.
ETS = mutable hash table outside the process heap. No path copying, no GC pressure from the table itself.
Tradeoff: data copied in/out of ETS on every access. Partially offsets the HAMT savings.
5,324ms
10M rows
x1.1
vs baseline

Mutable storage helps, but not if you pay for it on every access. We drop ETS in the combined version — with parallelism, each Task owns a local Map. This insight leads to the process dictionary later.

Why This Matters for 1BRC

Process isolation

Own heap, own GC. No locks, no mutexes. When a process dies, its heap is freed instantly.

Per-process GC

No stop-the-world. 10 workers doing millions of Map updates — each GC is independent.

Work stealing

Idle schedulers steal from busy queues. Automatic load balancing across all cores.

The BEAM was designed for concurrency. 35+ years of Ericsson telecom refinement. Scheduler, GC & process model scale linearly with cores. That's why Task.async_stream isn't just a convenience — it's leveraging a runtime built for this exact pattern.

File.stream! goes through a single GenServer (I/O server). Reads serialize even with parallel consumers.
:file.read :raw bypasses it — file reads cross from user space to kernel space via syscall (~1-5μs each). :raw minimizes these crossings.
Textbook embarrassingly parallel: partition the input, process independently, merge at the end.
x3.1 not x10 — Amdahl's Law: chunk alignment, merge phase, and I/O bandwidth cap the scaling.

Memory Optimizations

Reducing GC pressure and eliminating unnecessary allocations.

Key Copy
:binary.split returns sub-binaries — pointers into the original 1MB chunk. The chunk can't be GC'd while any sub-binary exists.
:binary.copy on the city name creates an independent ~10-byte binary. Frees the chunk for GC. Less memory pressure, better cache behavior.

Biggest Win

The Process Dictionary Breakthrough

Replacing immutable Maps with O(1) mutable per-process storage.

Before: Map (HAMT)

Map.update(acc, city, init, fn

  {min, max, count, sum} ->

    {min(min,t), max(max,t),

     count+1, sum+t}

end)

HAMT branching factor 32, depth ~2-3 for 413 keys. Every update copies the leaf-to-root path
10M rows = 20-30M temporary tuple allocations from path nodes. All short-lived, all in a hot loop
Per-process generational GC must sweep them all. At 1B rows, GC pauses become a measurable fraction of runtime
534 ms
10M rows (with key-copy)
x1.39
After: Process Dictionary

case :erlang.get(key) do

  :undefined ->

    :erlang.put(:binary.copy(key), init)

  {min, max, count, sum} ->

    :erlang.put(key, updated)

end

Flat hash table in the process control block. O(1) amortized, in-place update at runtime level
Zero temp allocations — no path copying, no new nodes. GC pressure → ~0
Generally discouraged (breaks referential transparency), but safe here: each Task is an isolated process
:binary.copy on new keys — sub-binary would keep parent 1MB chunk alive in memory

Lessons

Key Takeaways

Eight principles from the 1BRC optimization journey.

Isolate Changes

One optimization per branch. Measure each contribution independently before combining.

Binary > String for ASCII

:binary.split and pattern matching bypass Unicode overhead. ~2x faster split.

Proc Dict is the Fastest Map

O(1) mutable storage per process. Safe when each Task owns its own dictionary. The single biggest win.

Integers > Floats

Work with integers x10, divide only at the end. Avoids Float.parse entirely — ~2–3x faster conversion.

Raw Reads > File.stream!

:file.read with :raw bypasses the I/O server for direct kernel access.

Speedups Compound

Different bottleneck layers multiply: x1.4 × x3.1 = x6.4. Fixing I/O, parsing, and storage amplifies each.

Simpler Beats Cleverer

Dynamic work queue was slower than fixed partitions. Not every "improvement" improves performance.

Always Measure

Byte-range partitioning was slower at 10M rows but faster at 1B. Context and scale determine what wins.
